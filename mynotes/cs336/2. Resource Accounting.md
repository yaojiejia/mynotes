## 1. The two motivating back-of-envelope questions

These are the kind of question you should be able to answer by the end of the course. **The point isn't precision — it's getting the rough shape of things.**

### Q1: How long to train 70B params on 15T tokens with 1024 H100s?

```
FLOPs needed  = 6 × N_params × N_tokens = 6 × 70e9 × 15e12  = 6.3e24
Hardware rate = 1024 × 989.5e12 × MFU(0.5)                  ≈ 5.1e17 FLOP/s
Time          = 6.3e24 / 5.1e17 ≈ 1.24e7 s                  ≈ 143 days
```

### Q2: Largest model trainable on 8× H100 with AdamW?

```
Memory available = 8 × 80 GB = 640 GB
Bytes per param  = 2 (bf16 param) + 2 (bf16 grad) + 4 + 4 (fp32 Adam m, v) = 12
N_params         = 640e9 / 12 ≈ 53B
```

⚠️ Caveat: this ignores **activations**, which depend on batch size and sequence length.

## 2. Tensors and precision

**Everything is a tensor** — parameters, gradients, optimizer states, data, activations. Look at any released model (e.g. DeepSeek) and it's just a list of tensors, each with a shape and a **dtype**.

### Memory of a tensor
```
memory = numel × element_size
```
A 4×8 fp32 matrix = 32 × 4 = **128 bytes**. One feedforward matrix in GPT-3 ≈ **2.3 GB** — and that's an old model.

### Float formats

| Format | Bits | sign / exp / mantissa | Notes |
|---|---|---|---|
| **fp64** | 64 | 1/11/52 | "double precision" — scientific computing |
| **fp32** | 32 | **1/8/23** | "single precision", PyTorch default. The scientific-computing baseline |
| **fp16** | 16 | **1/5/10** | ⚠️ **Bad dynamic range** — only 5 exponent bits |
| **bf16** | 16 | **1/8/7** | ✅ Same dynamic range as fp32, worse resolution |
| **fp8** | 8 | E4M3 or E5M2 | Two variants — pick range vs. resolution. H100 / Transformer Engine |
| **nvfp4** | 4 | block-scaled | Only ~16 representable values, rescued by block scaling |

**Exponent bits = dynamic range. Mantissa bits = resolution.**

- **fp16 fails** because of range, not precision: `torch.tensor(1e-8, dtype=float16)` is literally `0`. Training in fp16 gives underflow, overflow, NaNs, instability. People did it back in the day; it was painful.
- **bf16 (2018)** fixes this by moving bits *from mantissa to exponent* — same total width, same range as fp32. **Deep learning is stochastic and sloppy anyway, so you don't need the resolution — you need to not overflow.** This is the sweet spot.
- **nvfp4 block scaling** (asked in class): within a block, each value has 4 bits of freedom; the whole block then gets a shared scale factor. So an individual value effectively has more than 4 bits of dynamic range — you just can't have one value huge and its neighbor tiny *within the same block*. **Nemotron 3 Super** was trained in fp4.
- **Low-bit inference ≠ low-bit training.** Quantizing a bf16-trained model down to 1–2 bits is much easier than *training* at that width. Nobody has trained a credible 1-bit LM.
- Much of fp8/fp4 isn't something you touch directly — it happens inside NVIDIA's stack.

### Mixed precision training (standard practice)
- **bf16** → parameters, activations, gradients
- **fp32** → optimizer states (stability: you're squaring and averaging over many steps)
- PyTorch `AMP` wraps your code and auto-casts: MatMuls are safe in bf16, things like `exp` are kept in fp32.

**Rule of thumb:** small model and you don't want to think about it → just use fp32. Otherwise **bf16 mixed precision**. Never plain fp16.

### Why lower precision is faster (three separate reasons)
1. Less memory to store.
2. Fewer bits to operate on (roughly ~2× per halving, but not always).
3. **Less memory to *move*** — which turns out to be the real one. See §5.

> Tensors default to **CPU**. Move them to GPU or you get no speedup.

## 3. einops — name your dimensions

Motivation: code like `x.transpose(-2, -1) @ y` is unreadable and easy to get wrong. **Use names instead of indices.** (Inspired by Einstein summation notation.)

### `einsum` — generalized MatMul with bookkeeping
```python
z = einsum(x, y, "seq1 hidden, hidden seq2 -> seq1 seq2")
```
**Rule: enumerate over every named variable, multiply the indexed entries, and sum out anything that does not appear on the right-hand side.** (Here `hidden` is summed.)

Batched version — note **no transpose needed**, the naming does it:
```python
z = einsum(x, y, "batch seq1 hidden, batch seq2 hidden -> batch seq1 seq2")
z = einsum(x, y, "... seq1 hidden, ... seq2 hidden -> ... seq1 seq2")   # ... = any # of batch dims
```
The `...` matters in LM code, where you routinely carry batch + sequence + head dims and want the same op to work regardless of rank.

### `reduce` — generalizes sum / mean / max / min
```python
y = reduce(x, "... hidden -> ...", "sum")
```
Same rule: the dim missing from the output gets reduced, with the named operation.

### `rearrange` — split / merge dimensions
Use when one dimension secretly encodes two (e.g. a flattened head dimension):
```python
x = rearrange(x, "... (heads hidden1) -> ... heads hidden1", heads=2)   # 8 -> 2 × 4
x = einsum(x, w, "... hidden1, hidden1 hidden2 -> ... hidden2")
x = rearrange(x, "... heads hidden2 -> ... (heads hidden2)")            # merge back
```
You must supply one of the sizes (`heads=2`) since 8 could split as 2×4 or 4×2. The **order inside the parens defines the row-major/column-major question** — it's not ambiguous, it's whatever order you wrote.

> ❓Q from class: is einops faster? **No — it's sugar.** It compiles down to the same primitives. The win is cognitive: no more transposes to reason about.

## 4. FLOPs accounting

### Terminology pet peeve
- **FLOPs** (lowercase s) = *floating-point operations* — a quantity of work done. "GPT-3 took ~3e23 FLOPs."
- **FLOP/s** = *operations per second* — hardware speed. "An H100 does 989 teraFLOP/s."

Write `/s` explicitly. `FLOPS` with a capital S is ambiguous and everyone abuses it.

### ⚠️ The spec-sheet trap
NVIDIA advertises H100 bf16 at **1979 teraFLOP/s** — but a footnote says *with sparsity*. **For dense, divide by 2 → 989.5 teraFLOP/s.** You'll see `/2` all over this lecture for that reason.

| | fp32 | bf16 / fp16 (dense) |
|---|---|---|
| **H100** | 67.5 TFLOP/s | 989.5 TFLOP/s |
| **A100** | 19.5 TFLOP/s | 312 TFLOP/s |

Note how bad fp32 is now — nobody optimizes that path anymore.

**Intuition anchor:** 8 H100s (one node) for one week ≈ **5e21 FLOPs**.

### The core formula
For `x: (B, D) @ w: (D, K)`:
```
FLOPs = 2 · B · D · K
```
The `2` = one multiply + one add per triple. (Strictly it's `D−1` additions, so `2BDK − BK`; ignore it.)

Rewrite it, because this is the whole game:
```
B = # data points / tokens
D·K = # parameters

⇒ forward FLOPs = 2 × (# tokens) × (# parameters)
```
This is the shape of `6ND` already forming.

### Everything else is cheap
Elementwise ops cost ~`numel` FLOPs. **No operation you meet is as expensive as MatMul for large enough matrices**, so for FLOP counting you can basically just count MatMuls. *(The important caveat comes when we count memory instead — §5.)*

> ❓Sub-cubic MatMul algorithms (Strassen etc.)? In practice the optimization effort goes into **co-designing with the hardware**, not asymptotics.
> ❓Is multiply more expensive than add? In hardware, basically the same.

### Timing it for real
```python
torch.cuda.synchronize()   # GPU runs async — without this your timings look impossibly fast
t0 = time.time()
op()
torch.cuda.synchronize()   # and again after
```
Repeat and average. Without the sync you're just timing a non-blocking launch call.

### MFU — Model FLOPs Utilization
```
MFU = (actual FLOP/s) / (promised FLOP/s)      # promised = already-halved dense spec number
```
- **≥ 0.5 on a real model → be happy.**
- A bare MatMul can reach ~0.8.
- **~0.1 → something is badly wrong, go fix it.**
- You never exceed the promise.

Compute it as (counted logical FLOPs) ÷ (wall clock) ÷ (spec FLOP/s). **Do this for your own model.**

## 5. ⭐ Arithmetic intensity — why MFU is only 0.5

### The picture
Data lives in **HBM**. Compute happens in the **accelerator cores**. Every op means: **move inputs up → compute → move results back.** So runtime depends on *two* hardware numbers:

| H100 | value |
|---|---|
| Compute | 1979e12 / 2 = **989.5e12 FLOP/s** |
| **Memory bandwidth** | **3.35e12 bytes/s** |

> This is the second reason memory size matters. The obvious one is "the model has to fit." The non-obvious one: **memory has to be *moved*, and moving it takes time — so size affects speed.**

### The model
Assume **communication and compute overlap perfectly** (start computing as soon as bytes arrive):
```
time ≈ max(comm_time, compute_time)
comm_time    = bytes_moved / (bytes/s)
compute_time = flops / (FLOP/s)
```
Real overlap is imperfect, but this is good enough for napkin math.

- `comm_time > compute_time` → **memory bound** (waiting on bits)
- `compute_time > comm_time` → **compute bound** (actually doing work)

### The two intensities

```
accelerator intensity  = (FLOP/s) / (bytes/s)     ← a property of the HARDWARE
arithmetic intensity   = flops / bytes_moved      ← a property of the ALGORITHM
```

**H100 accelerator intensity = 989.5e12 / 3.35e12 ≈ 295.**
👉 *Keep ~300 in your head: an H100 can do ~300 FLOPs in the time it takes to move one byte.*

```
arithmetic intensity < accelerator intensity  ⇒ memory bound
arithmetic intensity > accelerator intensity  ⇒ compute bound
```
(Algebraically identical to the time comparison — just cross-multiplied.)

### Worked table (bf16 = 2 bytes/element)

| Op | Bytes moved | FLOPs | Intensity | Verdict |
|---|---|---|---|---|
| **ReLU** (n) | 2n read + 2n write = 4n | n | **0.25** | 🔴 memory bound |
| **GELU** (n) | 4n | ~20n | **~5** | 🔴 memory bound |
| **Dot product** (n) | 2n + 2n + 2 | 2n − 1 | **~0.5** | 🔴 memory bound |
| **Matrix-vector** (n×n) | 2n + 2n² + 2n | 2n² | **~1** | 🔴 memory bound |
| **MatMul** (n×n) | 2n² + 2n² + 2n² = 6n² | 2n³ | **≈ n/3** | 🟢 compute bound (large n) |

### What this table is telling you
- **GELU costs the same wall-clock time as ReLU.** GELU does ~20× the arithmetic, but both are memory bound, so the extra math is *free*. Your intuition that "GELU is expensive" is wrong for the wrong reason.
- **Only MatMul escapes**, and only because you move `n²` bytes to do `n³` work → intensity grows as **O(n)**. **This is why everyone tells you to use big batches and big matrices.** Below the accelerator intensity, shrinking your matrices doesn't make anything faster — it's all the same. Above it, you're actually saturating the GPU.
- **Transformers are compute bound *by design*** — they're big MatMuls with a few things sprinkled between. The architecture was built for high arithmetic intensity.
- 🔮 **Inference foreshadowing:** generating one token at a time is a **matrix-vector** product → intensity ~1 → **memory bound**. Training processes the whole sequence at once → MatMul → compute bound. *This is the core reason decode is hard.*
- Intensity depends on **precision** too — fewer bytes per element shifts the ratio.
- **This answers "why is my MFU only 0.5":** the promised FLOP/s assumes you're doing nothing but compute. Every memory-bound stretch is time where the cores idle.

### Roofline plot
x-axis = arithmetic intensity, y-axis = achieved FLOP/s, one line per accelerator.
- Low intensity → a **sloped** region: you're capped by bandwidth, and achieved FLOP/s rises with intensity.
- Past the knee (at the accelerator intensity) → a **flat** ceiling at peak FLOP/s. You can't exceed the roof.

## 6. Training: compute accounting

### Setup — a plain deep network
Input `(B, D)`, then `L` layers of `(D, D)` MatMul + elementwise ReLU.
```
# params = D² · L
```

### Backward pass costs 2× forward
For one layer `h2 = einsum(h1, w2, "batch in, in out -> batch out")`:

Forward: `2 · B · D · D`

Backward has to compute **two** gradients:
```python
# 1. backward message: dL/dh1  (to pass down the chain)
h1_grad = einsum(h2_grad, w2, "batch out, in out -> batch in")

# 2. parameter gradient: dL/dw2
w2_grad = einsum(h2_grad, h1, "batch out, batch in -> in out")
```
Both enumerate the same three dims `(batch, in, out)` — only the summed-out dim differs — so **each costs the same as the forward MatMul**.

> 💡 einops kills the transpose confusion here. You never have to remember which of `dL/dh` or `W` gets transposed; you just write out the named dims and the shapes force the answer.

### ⇒ The 6ND formula
```
forward   = 2 × (# tokens) × (# params)
backward  = 4 × (# tokens) × (# params)      ← 2 gradients per layer
--------------------------------------------
total     = 6 × (# tokens) × (# params)
```
**That's where `6ND` comes from — literally just counting forward and backward.**

⚠️ **When it breaks:** this is a good approximation for Transformers *as long as context length isn't too large*. Long context adds an O(seq_len²) attention term this accounting misses. (A1 makes you do the careful Transformer version.)

## 7. Training: memory accounting

Four consumers, for the `D²L` deep net under bf16 + fp32 optimizer states:

| What | Formula | Bytes/param |
|---|---|---|
| **Parameters** | 2 · D² · L | 2 (bf16) |
| **Activations** | 2 · B · D · L | — scales with **batch size** |
| **Gradients** | 2 · (# params) | 2 (bf16) — same shape as params |
| **Optimizer state** | 4 · (# params) per moment | **fp32** for stability |

Optimizer state per parameter:
- **SGD**: 0
- **AdaGrad**: 4 bytes (second moment only)
- **Adam / AdamW**: **8 bytes** (first + second moment)

**Optimizer state is a large fraction of total memory.** But note the asymmetry: **memory serves two purposes** — (a) fitting in HBM, and (b) being shipped to the accelerator. Optimizer state isn't on the compute critical path, so **its size doesn't hurt your speed much — it just caps how big a model you can fit.**

> Why fp32 for optimizer state? People have tried bf16. You're squaring gradients and averaging over many steps; it isn't stable.

### The optimizer, mechanically (AdaGrad, 2011 — between SGD and Adam)
- **Momentum** = first moment of the gradient. **AdaGrad** = second moment. **Adam** = both.
- Optimizer state = per-parameter-group scratch storage the optimizer keeps across steps.
- AdaGrad step: accumulate `g² += grad²` into state, then update `p -= lr · grad / sqrt(g²)`.

## 8. Two ways to cut memory

### Gradient accumulation
Large batches help stability, but **activation memory scales with batch size**, so you OOM. Fix:
1. Split the batch into **micro-batches**.
2. Compute gradients on each and **don't zero them** — they accumulate.
3. Every `batch_size / microbatch_size` steps, step the optimizer and zero the grads.

Trivial code change; same effective batch size, much less activation memory.

### Activation checkpointing (a.k.a. gradient checkpointing / rematerialization)
Training stores activations for **all** layers by default (`2·B·D·L`), because backprop needs them. *(Inference doesn't — it only needs the current layer's, which is why inference memory looks so different.)*

**Idea:** in the forward pass keep activations for only a **subset** of layers; in the backward pass **recompute** the missing ones from the last checkpoint. Classic systems trade: **spend compute to save memory.**

```python
torch.utils.checkpoint.checkpoint(block, x)   # don't store this block's intermediates
```
E.g. checkpointing each `linear + ReLU` block means you don't store the pre-ReLU tensor → **~half the activation memory**, recovered cheaply in the backward pass.

**The trade-off curve** over `L` layers:

| Checkpoint every… | Activation memory | Recompute overhead |
|---|---|---|
| every layer (store all) | `L` | none |
| **√L layers** | **√L** | **√L** ← 🎯 balanced sweet spot |
| nothing | ~1 | `L²` (restart from the beginning each time) |

## Summary
1. **Everything is a tensor** — params, gradients, activations, optimizer state, data.
2. **einops** — name your dimensions; think in `einsum` / `reduce` / `rearrange` instead of transposes and axis indices.
3. **`6 × tokens × params`** FLOPs per training step = 2 forward + 4 backward. Demystified.
4. **Arithmetic intensity + roofline** diagnose memory bound vs. compute bound. **MatMuls are compute bound; basically everything else is memory bound.** Accelerator intensity ≈ 300 for an H100.
5. **MFU = actual / promised FLOP/s.** ≥0.5 is good; memory-bound stretches are what eat the rest.
6. **Gradient accumulation** and **activation checkpointing** reduce memory, which in turn lets you use bigger batches (→ higher intensity → better MFU).
